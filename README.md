# Andrei Fedoseev

Senior backend engineer in Valencia, Spain. I build PHP/Laravel services: APIs, queues and background jobs, SSO integrations, and the systems that keep releases running reliably.

In open source, I look for bugs in the tools I use, from AI SDKs and agent memory to queues and locks. Each report comes with a reproduction, a failing test and, where I can, a fix.

**Merged so far:** 15 fixes in [Symfony](https://github.com/symfony/symfony/pulls?q=is%3Apr+author%3Askybleak333+is%3Aclosed), 4 in [openai-php/client](https://github.com/openai-php/client/pulls?q=is%3Apr+author%3Askybleak333+is%3Amerged), 1 in the [official MCP SDK for PHP](https://github.com/modelcontextprotocol/php-sdk/pull/707). The [Hindsight](https://github.com/vectorize-io/hindsight) maintainer fixed all 5 of my bug reports, one [with me as co-author](https://github.com/vectorize-io/hindsight/commit/7c54d7cba6ec7a50078fae8669c55c424d0363d1).

## Backend infrastructure

- **[Symfony](https://github.com/symfony/symfony):** fifteen merged bug fixes in Messenger, Lock, Semaphore, RateLimiter and Scheduler, each with a failing test and a reproduction:
  - [#68021](https://github.com/symfony/symfony/pull/68021) RateLimiter: the sliding window counted reservations for later windows as hits that had already happened, so workers waiting for a reservation went over the limit: with 10 per minute, 50 workers got 60.
  - [#67993](https://github.com/symfony/symfony/pull/67993) Messenger: with `--fetch-size`, `--keepalive` covered only the message being handled, so the rest of the batch went to another worker and was handled twice (reproduced with two workers on PostgreSQL).
  - [#68020](https://github.com/symfony/symfony/pull/68020) and [#68022](https://github.com/symfony/symfony/pull/68022) Redis transport: after a failed read or reject, a worker with the new cooldown strategy kept running but never read again the messages Redis had already delivered to it.
  - [#68011](https://github.com/symfony/symfony/pull/68011) Semaphore: once a slot of a `LockStore` semaphore had expired and another process took it, `acquire()` still returned `true`, so two processes held a semaphore limited to one.
  - [#67994](https://github.com/symfony/symfony/pull/67994) Lock: once the PostgreSQL session was lost, `DoctrineDbalPostgreSqlStore` never gave that lock to the process again until it restarted.
  - [#68029](https://github.com/symfony/symfony/pull/68029) Lock: with a Predis client created from a DSN, Redis errors were taken for a success, so after a failover two processes could hold the same lock.
  - [#68025](https://github.com/symfony/symfony/pull/68025) Scheduler: after a restart, a cron task without a timezone moved to the timezone of the task that ran last, so a nightly 02:00 UTC job ran at 07:00.
  - [#68019](https://github.com/symfony/symfony/pull/68019) RateLimiter: the token bucket counted the wait from now instead of from its last refill, so `retryAfter` was up to a full interval late.
  - Also merged: `CompoundLimiter` accepting a hit that one of its limiters refused ([#68016](https://github.com/symfony/symfony/pull/68016)), a Redis keepalive check comparing milliseconds with seconds ([#68017](https://github.com/symfony/symfony/pull/68017)), MongoDB `isAcquired()` failing before the first `acquire()` ([#68027](https://github.com/symfony/symfony/pull/68027)), Memcached locks longer than 30 days expiring at once ([#68028](https://github.com/symfony/symfony/pull/68028)), a Scheduler worker crashing when its lock expired during a long run ([#68030](https://github.com/symfony/symfony/pull/68030)), `'P1M'` intervals running every 31 days ([#68026](https://github.com/symfony/symfony/pull/68026)).
  - Under review: [#68088](https://github.com/symfony/symfony/pull/68088), a follow-up the maintainer asked for (the token bucket's reset time); [#68089](https://github.com/symfony/symfony/pull/68089), a task added to a running Scheduler ran all its earlier slots at once (15 messages for an hourly task added in the afternoon); in Cache, [#68090](https://github.com/symfony/symfony/pull/68090), tagged items without expiry were read back as expiring in 2090, and [#68091](https://github.com/symfony/symfony/pull/68091), `ChainAdapter` still lost the expiry of items from `FilesystemAdapter` after #59947 was closed; in HttpClient, [#68095](https://github.com/symfony/symfony/pull/68095), a retried `PUT` or `POST` with a stream or generator body went out empty and the server accepted it without its payload, [#68096](https://github.com/symfony/symfony/pull/68096), curl sent a rewound `php://temp` body empty, [#68094](https://github.com/symfony/symfony/pull/68094), `CachingHttpClient` stored `Expires: 3600` as fresh until the year 3600, and [#68093](https://github.com/symfony/symfony/pull/68093), streaming cached and uncached responses together failed with a `TypeError` on 6.4.
- **[Monolog](https://github.com/Seldaek/monolog)** (under review): [#2095](https://github.com/Seldaek/monolog/pull/2095), `HtmlFormatter` dropped any message or context that was not valid UTF-8, so the error emails of `MailHandler` came without the message; [#2096](https://github.com/Seldaek/monolog/pull/2096), hourly log files named like `YmdH` still rotated only at midnight; [#2097](https://github.com/Seldaek/monolog/pull/2097), `PsrLogMessageProcessor` ignored its date format for Monolog and Carbon dates.
- **[php-amqplib#1248](https://github.com/php-amqplib/php-amqplib/pull/1248)** (under review): fixes [#1227](https://github.com/php-amqplib/php-amqplib/issues/1227) in the main PHP AMQP client. The heartbeat check counted the client's own writes, so a consumer whose network dropped never noticed. Reproduced with toxiproxy; opt-in, so proxies that send heartbeats differently (AMQProxy before 3.2.1) aren't affected. [#1249](https://github.com/php-amqplib/php-amqplib/pull/1249) fixes [#1243](https://github.com/php-amqplib/php-amqplib/issues/1243): the error handler around socket calls turned unrelated deprecations into exceptions. In the async client [bunny](https://github.com/jakubkulhan/bunny), [#237](https://github.com/jakubkulhan/bunny/pull/237) (under review): after one failed connect, every later `channel()` call hung forever.
- **[Predis](https://github.com/predis/predis)** (under review): [#1755](https://github.com/predis/predis/pull/1755): when Redis rejected a command queued in a transaction built with the fluent interface (OOM, `READONLY` after a failover), the connection stayed in `MULTI`, so every later command on it was queued and never ran. With persistent connections, the next request on that PHP-FPM worker got the same socket. [#1756](https://github.com/predis/predis/pull/1756): once a transaction had sent `WATCH` or `MULTI`, a lost connection made Predis retry the command on a new connection, outside the transaction. With Sentinel this happened with default options, and a check-and-set transaction then overwrote a change another client made after `WATCH`.
- **[laravel-queue-lab](https://github.com/skybleak333/laravel-queue-lab):** reproducible experiments with Laravel workers, rerun in CI every week: jobs that run twice after RabbitMQ's acknowledgement timeout, a frozen broker that `queue:work` doesn't notice, `rabbitmq:consume` ignoring SIGTERM in maintenance mode, and two Laravel 13 bugs: debounce `maxWait` that didn't force a single run in 60 s of steady dispatches, and a timeout counted twice against `maxExceptions` ([v0.5](https://github.com/skybleak333/laravel-queue-lab/releases/tag/v0.5.0)).
- **[vyuldashev/laravel-queue-rabbitmq#680](https://github.com/vyuldashev/laravel-queue-rabbitmq/pull/680)** (under review): fixes `rabbitmq:consume` for the Worker API changes in Laravel 11.52+, 12.59+ and 13.x. With the released v15.0.2 it doesn't process jobs on Laravel 13.31+. [#684](https://github.com/vyuldashev/laravel-queue-rabbitmq/pull/684) builds on it: in maintenance mode a paused `rabbitmq:consume` ignored SIGTERM, `queue:restart` and `--max-time`.
- **Queue reliability checks for other people's issues:** an [analysis of #664](https://github.com/vyuldashev/laravel-queue-rabbitmq/issues/664#issuecomment-6211004087) (the reported hang is really redelivery), an [independent check of PR #674](https://github.com/vyuldashev/laravel-queue-rabbitmq/pull/674#issuecomment-6239412564), and [measurements for php-amqplib#1227](https://github.com/php-amqplib/php-amqplib/issues/1227#issuecomment-6239409018).
