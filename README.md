# Andrei Fedoseev

Senior backend engineer in Valencia, Spain. I build PHP/Laravel services: APIs, queues and background jobs, SSO integrations, and the systems that keep releases running reliably.

In open source, I look for bugs in the tools I use and report them with a reproduction, a failing test and, where I can, a fix.

## Open source

- **[Hindsight](https://github.com/vectorize-io/hindsight)** (~60k stars, no outside pull requests): five bug reports with reproductions, four with patches and one with a failing test; the maintainer fixed all five, each within four days. For [#6337](https://github.com/vectorize-io/hindsight/issues/6337), concurrent retries that stored facts twice, the [fix](https://github.com/vectorize-io/hindsight/pull/6433) keeps my failing test, and the [merged commit](https://github.com/vectorize-io/hindsight/commit/7c54d7cba6ec7a50078fae8669c55c424d0363d1) lists me as co-author. [#6335](https://github.com/vectorize-io/hindsight/issues/6335) was fixed in [#6408](https://github.com/vectorize-io/hindsight/pull/6408), which follows my patch, and [#6409](https://github.com/vectorize-io/hindsight/pull/6409); [#6280](https://github.com/vectorize-io/hindsight/issues/6280) was [fixed with thanks](https://github.com/vectorize-io/hindsight/pull/6318); [#6231](https://github.com/vectorize-io/hindsight/issues/6231) shipped in v1.2.0; [#6235](https://github.com/vectorize-io/hindsight/issues/6235). Open, each with failing tests and a patch: [#6444](https://github.com/vectorize-io/hindsight/issues/6444) (the follow-ups #6408 left); [#6450](https://github.com/vectorize-io/hindsight/issues/6450) (re-running the new re-embed command with another model of the same size left vectors from both); [#6452](https://github.com/vectorize-io/hindsight/issues/6452) (retaining a document again undid the tags an extension had given its memories).
- **[Symfony](https://github.com/symfony/symfony)** (both merged): [#67993](https://github.com/symfony/symfony/pull/67993) in Messenger: with `--fetch-size`, `--keepalive` covered only the message being handled, so the rest of the batch went to another worker and was handled twice (reproduced with two workers on PostgreSQL). [#67994](https://github.com/symfony/symfony/pull/67994) in Lock: once the PostgreSQL session was lost, `DoctrineDbalPostgreSqlStore` never gave that lock to the process again until it restarted.
- **[hindsight-php](https://github.com/skybleak333/hindsight-php):** long-term memory for Laravel AI SDK agents on the open-source [Hindsight](https://github.com/vectorize-io/hindsight) server. It stores memories through the Laravel queue, and a retry never stores one twice; `Hindsight::fake()` makes it testable, and [v0.3](https://github.com/skybleak333/hindsight-php/releases/tag/v0.3.0) ships a Laravel Boost skill for coding agents. CI runs against real Hindsight 1.1 and 1.2 servers.
- **AI libraries for PHP:** [openai-php/client#833](https://github.com/openai-php/client/pull/833) (merged): streaming a response that calls a custom tool failed with `UnhandledMatchError`, because the streaming parser kept its own list of output types and it fell behind the one `create()` uses. Under review: [symfony/ai#2893](https://github.com/symfony/ai/pull/2893): `#[Assert\Regex]` turned into a JSON schema pattern that let more through than the constraint (`/^[a-z]+$/` became `[a-z]+`), so tool and structured-output schemas allowed values the validator then rejected. [prism-php/prism#1054](https://github.com/prism-php/prism/pull/1054) fixes [#990](https://github.com/prism-php/prism/issues/990): DeepSeek and Perplexity streams arrived all at once at the end, and any stream longer than the 30 s request timeout failed. [symfony/ai#2895](https://github.com/symfony/ai/pull/2895): the Redis vector store returned only about half of the documents a query found, 3 of 5 with the default limit. [symfony/ai#2896](https://github.com/symfony/ai/pull/2896): an agent whose tool returned nothing (`void`) failed with a `TypeError` after the tool had already run. [symfony/ai#2897](https://github.com/symfony/ai/pull/2897): `drop()` on the Neo4j store deleted every node in the database, not only the store's.
- **[MCP PHP SDK](https://github.com/modelcontextprotocol/php-sdk)** (official SDK, under review): [#707](https://github.com/modelcontextprotocol/php-sdk/pull/707): a stdio server handled a message larger than the pipe buffer in parts, so a tool call with 100 KB of arguments got parse errors and never an answer, and the client timed out.
- **[php-amqplib#1248](https://github.com/php-amqplib/php-amqplib/pull/1248)** (under review): fixes [#1227](https://github.com/php-amqplib/php-amqplib/issues/1227) in the main PHP AMQP client. The heartbeat check counted the client's own writes, so a consumer whose network dropped never noticed. Reproduced with toxiproxy; opt-in, so proxies that send heartbeats differently (AMQProxy before 3.2.1) aren't affected. [#1249](https://github.com/php-amqplib/php-amqplib/pull/1249) fixes [#1243](https://github.com/php-amqplib/php-amqplib/issues/1243): the error handler around socket calls turned unrelated deprecations into exceptions. In the async client [bunny](https://github.com/jakubkulhan/bunny), [#237](https://github.com/jakubkulhan/bunny/pull/237) (under review): after one failed connect, every later `channel()` call hung forever.
- **[Predis](https://github.com/predis/predis)** (under review): [#1755](https://github.com/predis/predis/pull/1755): when Redis rejected a command queued in a transaction built with the fluent interface (OOM, `READONLY` after a failover), the connection stayed in `MULTI`, so every later command on it was queued and never ran. With persistent connections, the next request on that PHP-FPM worker got the same socket. [#1756](https://github.com/predis/predis/pull/1756): once a transaction had sent `WATCH` or `MULTI`, a lost connection made Predis retry the command on a new connection, outside the transaction. With Sentinel this happened with default options, and a check-and-set transaction then overwrote a change another client made after `WATCH`.
- **[laravel-queue-lab](https://github.com/skybleak333/laravel-queue-lab):** reproducible experiments with Laravel workers, rerun in CI every week: jobs that run twice after RabbitMQ's acknowledgement timeout, a frozen broker that `queue:work` doesn't notice, `rabbitmq:consume` ignoring SIGTERM in maintenance mode, and two Laravel 13 bugs: debounce `maxWait` that didn't force a single run in 60 s of steady dispatches, and a timeout counted twice against `maxExceptions` ([v0.5](https://github.com/skybleak333/laravel-queue-lab/releases/tag/v0.5.0)).
- **[vyuldashev/laravel-queue-rabbitmq#680](https://github.com/vyuldashev/laravel-queue-rabbitmq/pull/680)** (under review): fixes `rabbitmq:consume` for the Worker API changes in Laravel 11.52+, 12.59+ and 13.x. With the released v15.0.2 it doesn't process jobs on Laravel 13.31+. [#684](https://github.com/vyuldashev/laravel-queue-rabbitmq/pull/684) builds on it: in maintenance mode a paused `rabbitmq:consume` ignored SIGTERM, `queue:restart` and `--max-time`.
- **Queue reliability checks for other people's issues:** an [analysis of #664](https://github.com/vyuldashev/laravel-queue-rabbitmq/issues/664#issuecomment-6211004087) (the reported hang is really redelivery), an [independent check of PR #674](https://github.com/vyuldashev/laravel-queue-rabbitmq/pull/674#issuecomment-6239412564), and [measurements for php-amqplib#1227](https://github.com/php-amqplib/php-amqplib/issues/1227#issuecomment-6239409018).
